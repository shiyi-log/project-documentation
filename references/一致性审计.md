# 文档与项目实现的一致性审计

本参考文档用于生成文档、API、Schema、迁移、部署、运行手册和其他可能与实现漂移的文档。目标不是证明项目“已经上线”，而是证明文档中的具体声明能在固定版本的多类来源中被复核。

## 证据顺序

优先按下面的顺序确定规则归属；如果来源冲突，要记录冲突，不要静默选择最方便的文件：

1. 实现代码、Schema、迁移和生成器源码；
2. 配置、构建脚本、CI、部署清单和依赖清单；
3. 测试、契约测试、快照、OpenAPI/GraphQL/类型生成源；
4. README、运行手册、API 文档、架构说明和发布说明；
5. 外部权威文档或平台页面，必须标注来源和抓取日期。

文档是待验证声明，不是默认权威。生成文件只有在能追溯到生成脚本、输入 Schema 或实现代码时，才可以作为生成权威。

## 每个项目的最小证据矩阵

至少记录三类独立来源，生成文档或高风险文档优先记录四类：

| 证据类别 | 典型路径 | 要回答的问题 |
|---|---|---|
| 文档 | `README.md`、`docs/`、API/运行手册 | 文档声称了什么？受众和边界是什么？ |
| 实现 | `src/`、`app/`、`backend/`、`cmd/`、`packages/` | 代码实际暴露了什么入口、状态和行为？ |
| 配置/自动化 | `pyproject.toml`、`package.json`、`Makefile`、CI、Docker | 命令、端口、版本、构建和部署如何被定义？ |
| 测试/生成权威 | `tests/`、Schema、OpenAPI、生成脚本、快照 | 哪个测试或输入文件能复核文档声明？ |

单一文件、单元测试通过、文档网站成功构建或 HTTP 200 都不能替代这张矩阵。

## 检查步骤

1. 固定项目提交 SHA、默认分支和抓取日期。
2. 读取文档中的具体声明：命令、路径、端口、版本、API 字段、状态转换、迁移顺序、失败恢复和兼容性。
3. 在实现、配置/自动化和测试/生成权威中分别定位这些声明。
4. 对找不到、互相冲突或只能通过假设解释的声明，保留路径、命令和冲突文本，并标记 `partial`、`blocked` 或 `not-run`。
5. 只在四类来源可以相互定位且没有未解释冲突时标记 `verified`。
6. 单独记录未执行的浏览器、真实数据库、外部 Provider、链上、Telegram、CI、发布和生产检查。

## 项目级状态

- `verified`：固定提交上至少三类、优选四类来源可相互定位，检查项没有未解释冲突。
- `partial`：来源齐全但有未解决命令、路径、端口、版本或生成同步问题。
- `not-run`：计划检查但本次没有执行，必须说明原因和复现命令。
- `blocked`：前置条件、网络、权限或快照不可用，不能用猜测代替结果。
- `not-implemented`：文档描述了计划功能，但实现或生成源明确不存在。

状态是项目级摘要，不得掩盖具体证据缺口。

## 百项目规模验证

当用户要求大型项目、全量验证或至少 100 个项目时：

- 使用固定清单，项目数不少于 100，仓库唯一；
- 每个项目记录固定 SHA、默认分支、证据路径、检查命令、状态和限制；
- 按项目类型分批并行，但每批只写自己的临时结果；
- 主线程合并并复核仓库去重、SHA 完整性和状态原因；
- 汇总报告必须包含项目级表格、状态统计、失败样本、阻断项、未运行项和可复现命令；
- 不得把抽样项目、目录数量或 GitHub 页面可访问性描述成 100 个项目已完成验证。

## 自动修订闭环

发现技能缺口时，按下面的最小闭环处理：

1. 先写一个能复现错误判断的场景；
2. 在未修订技能的情况下记录 RED 观察；
3. 从多个项目失败样本提炼跨项目规则；
4. 只修改技能正文、参考文档或验证器中必要的部分；
5. 重跑场景和验证器，记录 GREEN 结果；
6. 将剩余限制写入中文报告和 CHANGELOG；
7. 提交前运行打包检查、结构检查、报告汇总和 `git diff --check`。

不要把某个仓库的特殊路径硬编码成普遍规则，也不要为了让报告变绿而删除失败项目。
