# 百项目文档一致性验证与技能修订实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 为 `project-documentation` 技能建立可复现的多源文档一致性验证流程，至少核验 100 个真实项目，并根据失败证据自动修订技能。

**架构：** 使用固定项目清单与提交 SHA 作为验证输入；每个项目至少收集文档、实现、配置/自动化、测试或生成源四类证据，输出结构化中文结果。批次验证在独立临时目录并行执行，主线程只负责合并报告、修订技能、运行全量检查和提交推送。

**技术栈：** Python 3 标准库、Git、GitHub 公开仓库浅克隆、Markdown/JSON、现有 `tests/validate_skill.py` 与 Codex `quick_validate.py`。

**规格：** 本用户目标（当前会话目标）以及仓库现有 `SKILL.md`、`references/quality-checklist.md`、`tests/pressure-scenarios.md`。

## 全局约束

- 验证对象必须是至少 100 个不同的真实项目，记录仓库、固定提交 SHA、默认分支和抓取日期。
- 每个项目不能只读一个文件；至少交叉检查文档、实现代码、配置或自动化、测试或生成权威中的三类，优先四类。
- 所有新增或修改的仓库文档（技能正文除外）使用中文；`SKILL.md` 可以继续使用英文。
- 生成文档、API、迁移、部署和运行手册的结论必须区分 `verified`、`partial`、`not-run`、`blocked`、`not-implemented`。
- 验证脚本和原始证据放在临时目录；仓库只保留清单、汇总报告、失败样本和可复现脚本。
- 不写入任何密钥、令牌、Cookie、私钥、密码或未脱敏个人数据。
- 每个可接受批次完成后先生成报告，再提交；不允许长期保留大量未提交文件。
- 不把本地静态证据、HTTP 200、单元测试或文档构建成功表述为生产或发布证明。

### 任务 1：建立中文验证场景与失败基线

**文件：**
- 创建：`tests/scenarios/生成文档多源一致性.md`
- 修改：`tests/pressure-scenarios.md`
- 测试：`tests/validate_skill.py`

**接口：**
- 场景输入：项目文档、实现、配置/自动化、测试/生成源。
- 场景输出：项目级证据矩阵和明确的缺失/阻断标签。

- [ ] **步骤 1：编写失败场景**

  场景必须要求代理处理一个文档声称、实现代码、配置/自动化和测试/生成源互相不一致的项目，并明确禁止只凭 README 下结论。

- [ ] **步骤 2：运行现有验证器确认场景未被覆盖**

  运行：`python3 tests/validate_skill.py`

  预期：当前基础验证可以通过，但不会检查 100 项目、多源证据或中文报告要求；把这个缺口写入场景文件。

- [ ] **步骤 3：记录 RED 观察**

  在场景文件中记录当前技能的可见缺口，不修改生产技能正文。

### 任务 2：实现项目清单与多源证据收集器

**文件：**
- 创建：`tools/validate_project_corpus.py`
- 创建：`tests/project-corpus.json`
- 创建：`tests/project-corpus.schema.json`

**接口：**
- `python3 tools/validate_project_corpus.py --manifest tests/project-corpus.json --output <dir>`
- 清单每项至少包含 `repo`、`default_branch`、`commit`、`docs`、`implementation`、`configuration`、`tests_or_generated_authority`。
- 输出每项目 JSON 记录和批次汇总 Markdown。

- [ ] **步骤 1：先写清单结构测试**

  测试至少断言：项目数不少于 100、仓库唯一、SHA 非空、四类证据字段存在、状态值来自允许集合。

- [ ] **步骤 2：运行测试确认失败**

  运行：`python3 tests/validate_skill.py` 和清单结构测试；在清单尚未创建前确认失败原因是缺少新资产而不是测试错误。

- [ ] **步骤 3：实现固定 SHA 清单加载**

  支持浅克隆或等价的只读快照，默认不修改任何上游仓库；网络失败记录为 `blocked`，不伪造通过。

- [ ] **步骤 4：实现四类证据发现**

  发现 README/文档入口、源码目录、构建/依赖/CI/部署配置、测试/Schema/OpenAPI/文档生成配置，并记录实际路径和文件摘要。

- [ ] **步骤 5：实现交叉检查**

  至少检查文档中的本地路径、命令、脚本入口、端口/版本声明与实现或配置是否可定位；不能定位时输出 `partial` 或 `not-run`，并保留原因。

- [ ] **步骤 6：运行最小样本**

  先用 3 个固定项目验证输出结构，再扩展到完整 100 项目清单。

### 任务 3：并行完成 100 个真实项目验证

**文件：**
- 临时输出：`/tmp/project-documentation-validation-20260927/batch-*.json`
- 仓库汇总：`docs/verification/百项目文档实现一致性验证-20260927.md`

**接口：**
- 每批 10–20 个项目，项目之间不得共享可写状态。
- 每项记录至少四类证据路径、固定 SHA、验证命令、状态、失败原因和限制。

- [ ] **步骤 1：划分批次**

  按 CLI、库、多服务应用、平台、基础设施、文档生成工具等类别分批，确保至少 100 个不同仓库。

- [ ] **步骤 2：并行运行批次**

  每个批次只写自己的临时目录；代理不得修改仓库跟踪文件，不得提交虚构结果。

- [ ] **步骤 3：主线程复核批次结果**

  检查仓库唯一性、SHA 可复现性、证据类别完整性、`blocked`/`not-run` 是否有原因，以及是否存在把单文件结果升级为项目结论的错误。

- [ ] **步骤 4：生成中文汇总报告**

  报告包含方法、清单、项目级结果表、按项目类型统计、失败样本、外部网络限制、未运行项和可复现命令。
