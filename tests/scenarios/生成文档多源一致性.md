# 生成文档多源一致性验证场景

## 目的

验证代理在面对“文档由工具生成，但实现已经变化”的项目时，是否会把文档、实现、配置/自动化和测试/生成源作为独立证据交叉核对，而不是只读取 README 或单一生成文件。

## 输入

构造一个公开项目快照，至少包含：

1. `README.md`：宣称启动命令为 `make serve`，监听 `8080`。
2. `src/`：实际入口为 `python -m app`，默认监听 `8081`。
3. `pyproject.toml`：脚本入口为 `app-cli = "app.cli:main"`。
4. `.github/workflows/ci.yml`：CI 执行 `pytest -q`。
5. `tests/`：断言默认端口为 `8081`。
6. `docs/` 或 OpenAPI/Schema 文件：由脚本生成，声明必须与实现和测试保持同步。

## 失败基线要求

未加载增强规则时，记录代理是否出现以下错误：

- 只读取 README 或生成文档便下结论；
- 把文档构建成功当成实现一致；
- 把单元测试通过当成部署或生产接受；
- 没有记录配置/自动化和测试/生成源；
- 没有列出文档与实现冲突的具体路径；
- 没有标记 `partial`、`not-run` 或 `blocked`；
- 没有形成项目级证据矩阵。

## 通过标准

加载增强规则后，代理必须：

- 明确列出文档、实现、配置/自动化、测试/生成源四类证据；
- 指出 `8080` 与 `8081` 的冲突以及 `make serve` 与实际入口的差异；
- 以实现/配置/测试作为当前行为证据，不把 README 当作唯一权威；
- 对未执行的浏览器、部署或生产检查写明 `not-run`；
- 输出可复核的文件路径、命令、提交 SHA 和限制；
- 将结论写入中文验证报告，并说明是否需要修正文档、实现或生成流程。

## 扩展验证

将同一方法应用到至少 100 个不同真实项目。每个项目至少记录三类独立来源，优先四类来源；任何缺失都必须保留原因，不得用“项目结构看起来正确”替代证据。
